User Guide

Purpose, audience, prerequisites, concepts, and user-facing outcomes.

What this module is for

Execution runtime for agent definitions, agent runs, tool resolution, lifecycle tracking, and human-review gating.

Who should use it

  • Business users performing approved tasks supported by this module.
  • Application administrators configuring module behavior within granted permissions.
  • Support and operations personnel diagnosing user-impacting issues.

Before using the module

  1. Sign in with the organization-approved identity method.
  2. Confirm the correct tenant or organizational context.
  3. Confirm the required role or permission for the intended task.
  4. Use approved data only, following classification and retention requirements.
  5. For state-changing activity, note the request, record, or workflow identifier for audit and support.

Core concepts

  • Agent definitions
  • Agent runs
  • Tool resolution
  • Human review

Expected user experience

  • Users see only records and actions authorized for the active tenant and role.
  • Validation messages identify correctable input problems without exposing internal details.
  • State-changing operations create an auditable result and show a stable record identifier.
  • Asynchronous work exposes pending, completed, and failed states rather than implying immediate success.

User safety rules

  • Do not enter secrets, tokens, passwords, or connection strings in free-text fields.
  • Do not upload content outside the approved file type, size, classification, and retention policy.
  • Do not retry a state-changing action repeatedly if the result is uncertain; use the record identifier and status page first.
  • Report missing access rather than using another person's account or tenant.

How-To Procedures

Task patterns for this module. Replace verification markers with exact deployed UI and API behavior.

How to find and open a record

  1. Open the GDX portal and navigate to this module. Verification required: exact menu label and route.
  2. Use the module search or filter controls. Enter a stable identifier when available.
  3. Confirm the record belongs to the intended tenant, product, workflow, or business context.
  4. Open the record and review status, owner, timestamps, and available actions.
  5. If the record is not visible, verify role, assignment, tenant, and filter settings before escalating.
Expected result: The authorized record opens with current status and permitted actions.

How to create or submit a record

  1. Select the module's create, new, start, or submit action. Verification required: exact action name.
  2. Complete required fields using approved data.
  3. Review generated validation, routing, approval, or classification information.
  4. Submit once. Preserve the returned identifier and confirmation.
  5. Track asynchronous processing from the status or work-inbox view.
Expected result: A new record is created, an identifier is returned, and any downstream workflow or background processing is visible.

How to update or progress work

  1. Open the current record and confirm the latest revision and status.
  2. Select only an action allowed by the displayed state and assigned role.
  3. Enter the required reason, comment, evidence, or decision.
  4. Submit once and confirm the resulting state, audit entry, and notifications.
  5. If an integration is pending, monitor delivery or synchronization status rather than resubmitting.
Expected result: The state change is recorded atomically and downstream work is traceable.

How to request support

  1. Capture the record identifier, tenant, timestamp, action attempted, and displayed error code.
  2. Do not copy secrets or sensitive payloads into the support request.
  3. Include the correlation ID when shown.
  4. State whether the issue is reproducible and whether another authorized user sees the same behavior.
  5. Follow the approved support channel and severity process. Verification required: support queue and escalation route.

Change-impact checklist

  • Identify the authoritative model and service layer.
  • Confirm tenant scoping and object authorization.
  • Use explicit serializer or schema allowlists.
  • Preserve transaction and concurrency semantics.
  • Move external side effects behind an outbox or durable job.
  • Add idempotency for retried state changes.
  • Version events, APIs, workflow artifacts, prompts, and schemas.
  • Update migrations and test fresh and supported upgrade paths.
  • Add structured telemetry without sensitive data.
  • Update user, API, operations, and troubleshooting documentation.

Local development workflow

  1. Use the repository's approved Python and Node versions. Verification required: exact versions.
  2. Create the approved local environment and resolve secrets through local references, never committed values.
  3. Start required dependencies such as PostgreSQL and Redis using the repository's approved container configuration.
  4. Apply migrations and run deployment checks.
  5. Run module-specific unit, integration, contract, security, and migration tests.
  6. Exercise the changed behavior through the UI or API with at least two tenants or authorization contexts when relevant.
  7. Verify logs, traces, metrics, outbox records, retries, and failure handling.
Procedural limitation: Exact shell commands and version numbers are intentionally not invented here. Publish those commands only after verifying the checked-in README, dependency lockfiles, settings modules, Docker configuration, and CI pipeline.

Definition of done

  • Functional acceptance criteria pass.
  • Cross-tenant and permission-negative tests pass.
  • Fresh install and supported migration path pass.
  • API/schema/event compatibility is reviewed.
  • Telemetry and runbooks cover failure modes.
  • Documentation identifies the build and environment used for verification.
